**1. Power BI**

Звіт побудований у Power BI Desktop. Джерелом даних є Excel-файл, розміщений у цьому GitHub-репозиторії та підключений через Power Query за допомогою raw.githubusercontent.com.

_Під час оновлення даних даних достатньо обрати тип автентифікації **Anonymous**._
GitHub було обрано замість Power BI Service, щоб результат не був залежним від ліцензій або прав доступу і був доступний для перевірки з одного репозиторія.

Для моделі було використано схему "зірка" і додаткову окрему таблицю з DAX-мірами для зручності.

Дашборд містить:
 - кількість звернень по місяцях;
 - частку SLA-порушень;
 - середній час виконання за типами звернень;
 - кількість звернень за відповідальними;
 - розподіл оцінок користувачів;
 - KPI: загальна кількість звернень, % порушень SLA, середній час виконання і середня оцінка користувачів.

Додано фільтри по типу звернення, пріоритету, статусу і відповідальним.
Додатково з мого боку було додано фільтр по даті.

Додатково реалізовано:
 - _% порушень SLA за пріоритетом_ - для виявлення проблем з дотриманням SLA за рівнями пріоритету;
 - _% порушень SLA за відповідальним_ - для порівняння SLA-показників між відповідальними.

**2. SQL**

У папці 02_sql знаходяться два запити: 1) середній час виконання за типами звернень; 2) кількість SLA-порушень по місяцях.

**3. Підхід і висновки**

Дані було завантажено через Power Query, очищено та трансформовано у схему "зірка". Основні показники зроблені через DAX-міри, а потім побудовано дашборд з обов'язковими і додатковими аналітиками.

Дашборд дозволяє керівництву оцінити динаміку навантаження, дотримання SLA, швидкість виконання звернень, розподіл навантаження між відповідальними і рівень задоволеності користувачів.

Основною особливістю даних була відсутність унікального ID звернення, тому було створено технічний варіант ідентифікатора.

Загалом, дашборд показує, що основною потенційною проблемною зоною є дотримання SLA - порушення зафіксовано у 45,5% звернень. Найвищий рівень порушень спостерігається у травні (60%) та для звернень із середнім пріоритетом (52%). Також помітна різниця між відповідальними: % порушень SLA варіюється від 50% до 53%, що може бути приводом для детальнішого аналізу розподілу навантаження та процесів обробки звернень.

В той самий час явних кореляцій і прямого зв'язку між часом виконання та фактом SLA-порушення в наданих даних не виявлено тому при прийнятті рішень було би корисно додатково уточнити бізнес-правила розрахунку SLA.

Використані інструменти: Power BI Desktop, Power Query, DAX, T-SQL, GitHub
